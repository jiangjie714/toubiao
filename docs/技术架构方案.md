## 一、设计目标与原则

### 1.1 目标（对应商业化需求）

| 需求 | 技术目标 | 验收锚点 |
|---|---|---|
| 数据更丰富 | Tender 8 字段 → 16 字段 + 3 个新实体（Project/Attachment/OrgContact）+ 原文快照 | 详情页展示金额/编号/联系方式结构化数据 |
| 来源更多 | 2 源 → M0 末 6 源 → M1 末 10+ 源；新增源的边际成本 ≤ 0.5–2 人日 | 只写 config + DB 配置即可接入新源 |
| 精细化配置管理 | 配置 DB 化、在线编辑、热更新、版本化回滚、dry-run、健康分、告警 | 源失效 30 分钟内告警；改配置无需重启 |
| 采集技能体系 | 声明式 extraFields、detail.extraction 结构化抽取、技能版本管理 | 新增一个抽取字段零代码变更 |

### 1.2 设计原则

1. **配置即数据**：技能配置从「文件系统静态 YAML」升级为「DB 版本化记录为准绳，文件仅作开发态」——热更新、版本回滚、在线编辑的共同前提
2. **同一解析路径**：dry-run 与正式抓取走完全相同的解析代码（RunContext 抽象），杜绝「测试通过、上线跑偏」
3. **声明式优先**：字段扩展、抽取规则全部落在 config；只有类型转换器（金额/日期解析）和聚合算法是代码
4. **字段级而非记录级**：入库更新从「整条覆盖」升级为「字段级 diff + 置信度仲裁」，保护人工修正数据
5. **礼貌抓取不动摇**：每源限速/并发可配但默认保守；不破解、不伪造登录态（合规红线）

### 2.2 与现状的组件映射

| 现状 | v2 变化 |
|---|---|
| `crawler/worker.ts` 全局 node-cron | 拆为 `scheduler.ts`（due 检查）+ `queue.ts`（CrawlTask 表）+ `worker.ts`（进程壳 + TaskPool） |
| `runner.ts` 整条硬编码管道 | 拆出 `extraction.ts`（结构化抽取）、`projects.ts`（聚合）、`storage.ts`（存储接口）、`persist.ts`（字段级入库），runner 仅保留编排 |
| `loadSkillConfig()` 读文件 | `config-loader.ts` 读 DB SkillRevision（文件模式降级为 `--file` 开发旗标） |
| `upsertTender()` 全量覆盖 | 字段级 diff + 置信度仲裁 |
| 手写 YAML 校验 | zod schema 校验器 `schema.ts` |
| 无告警 | `health.ts` + `alerts.ts` |

## 三、数据模型设计

> 以下为 Prisma schema v2 增量。前提：provider 已切换 `postgresql`（第九章，M0 第一周完成）。

### 3.1 Tender 扩展（新增 9 字段 + 3 索引）

```prisma
model Tender {
  id             Int       @id @default(autoincrement())
  // ……现有字段不变：title/type/provinceCode/cityCode/publishDate/expireDate/
  //   purchaser/agency/sourceName/sourceUrl(unique)/content/createdAt/updatedAt

  // ── v2 结构化字段 ────────────────────────────────
  projectNo       String?                        // 项目/采购编号
  budgetAmount    Decimal?  @db.Decimal(14, 2)   // 预算金额（元）
  awardAmount     Decimal?  @db.Decimal(14, 2)   // 中标金额（元）
  openTime        DateTime?                      // 开标时间
  industryCode    String?                        // 行业分类（→ IndustryDict）
  winningSupplier String?                        // 中标供应商
  contentHtml     String?                        // 原文 HTML 快照（≤200KB 截断）
  projectRefId    Int?                           // → Project.id

  // ── 数据质量 ────────────────────────────────────
  fieldsConfidence Json?                         // {"budgetAmount":0.8,"openTime":0.6}
  fieldSources     Json?                         // {"budgetAmount":"ccgp",...}

  @@index([projectNo])
  @@index([projectRefId])
  @@index([publishDate, type])
}
```

设计要点：

- **Decimal 不被 SQLite 支持**（Prisma 层面），是第九章 PG 迁移的前置理由
- `contentHtml` 上限 200KB（超出截断并记 `contentHtmlTruncated=true`）；归档策略见 8.4
- `fieldsConfidence / fieldSources` 用 JSONB（PG 原生），key 为字段名——不做 EAV 宽表，字段集合仍由 schema 显式管理，JSON 只承载元数据
- `industryCode` 配字典表 `IndustryDict(code, name, parentId)`，种子 ≈20 个一级分类（医疗设备/IT/工程施工/办公物资…），后台运营维护
- migration 时存量数据整体置 `fieldsConfidence = {"*":0.5}`（无抽取元数据的遗留值），避免误当可信

## 四、采集技能体系 v2

### 4.1 配置 Schema v2（`crawler/types.ts` 升级为 zod 校验）

```ts
// 字段映射：在现有 FieldSpec 基础上增加 const 常量形态
export type FieldSpec =
  | string                                                // json 点路径
  | {
      selector?: string;
      attr?: string;                                      // text|html|href|src|…
      regex?: string;
      const?: string;                                     // v2：常量值（province: "河南"）
    };

// 开放式扩展字段：key 必须在 EXTRA_FIELD_TARGETS 白名单内
export type ExtraFields = Record<string, FieldSpec>;

// 详情结构化抽取：对详情页 DOM/正文执行，支持选择器与纯正则两通道
export type ExtractionSpec = { selector?: string; attr?: string; regex: string };

export type ListConfig = {
  type: "NOTICE" | "RESULT" | "CHANGE" | "INQUIRY";
  mode: "html" | "json";
  url?: string;
  firstPageUrl?: string;
  request?: { method: "GET" | "POST"; url: string; headers?: Record<string,string>; form?: Record<string,string> };
  startPage?: number;
  maxPages?: number;
  parse: {
    itemSelector?: string;
    itemsPath?: string;
    fields: { title: FieldSpec; url: FieldSpec; date?: FieldSpec; province?: FieldSpec;
              city?: FieldSpec; purchaser?: FieldSpec; agency?: FieldSpec; hint?: FieldSpec };
    extraFields?: ExtraFields;                            // ★ v2 新增
  };
  detail?: {
    contentSelector: string;
    removeSelector?: string;
    extraction?: Record<string, ExtractionSpec>;          // ★ v2 新增
  } | null;
};

export type SkillConfig = {
  source: { name: string; baseUrl: string };
  settings: {
    requestDelayMs?: number; timeoutMs?: number; retries?: number; maxPages?: number;
    headers?: Record<string,string>; userAgent?: string;
    scheduleCron?: string; proxyPolicy?: string;          // ★ v2（可被 DB 覆盖）
  };
  lists: ListConfig[];
};
```

### 4.2 extraFields 白名单（扩展字段的唯一入口）

**设计决策**：extraFields 不做「任意列直通」，而是白名单映射——key 是语义名，执行器按语义做类型转换与入库。数据质量有统一守门员，新增字段无需改 runner。

```ts
// crawler/extraction.ts
export const EXTRA_FIELD_TARGETS = {
  projectNo:       { column: "projectNo",       type: "string"   },
  budgetAmount:    { column: "budgetAmount",    type: "decimal"  },  // "1,490,000.00"/"149万元" → number
  awardAmount:     { column: "awardAmount",     type: "decimal"  },
  openTime:        { column: "openTime",        type: "datetime" },
  industryCode:    { column: "industryCode",    type: "industry" },  // 文本 → 字典最长匹配
  winningSupplier: { column: "winningSupplier", type: "string"   },
  contactPhone:    { column: "OrgContact.phone",   type: "phone"  },   // 复合目标 → OrgContact
  contactEmail:    { column: "OrgContact.email",   type: "email"  },
  contactAddress:  { column: "OrgContact.address", type: "string" },
} as const;
```

类型转换器职责：`decimal` 处理「1,490,000.00 / 149.5万元 / 3000 元」三种写法（万 → ×10000）；`datetime` 复用 `dates.ts`；`phone` 清洗分隔符与全角字符；`industry` 字典最长匹配，未命中返回 null 并计数（后台运营补字典）。

**置信度规则**：config 显式配置抽得 = **0.8**；内建兜底规则（4.3）抽得 = **0.6**；人工录入/校对 = **1.0**。

### 4.3 内建兜底抽取

某源 config 未写 `detail.extraction` 时，对正文启用内建规则（保证新源「零配置也有基础结构化」）：

```ts
const BUILTIN_EXTRACTION: Record<string, ExtractionSpec> = {
  projectNo:       { regex: '(?:项目编号|采购编号|招标编号)[：:]\\s*([A-Za-z0-9\\-—]{6,40})' },
  budgetAmount:    { regex: '(?:预算金额|最高限价)[（(]?[^)）]*[)）]?[：:]\\s*([\\d,，.]+)\\s*(万)?元?' },
  expireDate:      { regex: '(?:投标|响应文件递交|递交).{0,6}截止(?:时间|日期)[：:]?\\s*(\\d{4}年?\\d{1,2}月?\\d{1,2}日?)' },
  openTime:        { regex: '(?:开标时间|开启时间)[：:]\\s*(\\d{4}年\\d{1,2}月\\d{1,2}日[^，,。\\s]{0,10})' },
  winningSupplier: { regex: '中标(?:供应商|人)[：:]\\s*([^\\s，,。；;]{4,40})' },
  contactPhone:    { regex: '(?:联系电话|联系方式|电\\s*话)[：:]\\s*([\\d\\-—()]{7,20})' },
  contactEmail:    { regex: '[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\\.[A-Za-z]{2,}' },
  contactAddress:  { regex: '(?:地址|通讯地址)[：:]\\s*([^\\s]{6,60})' },
};
```

> 内建规则是保底，各源 SKILL.md 鼓励用 config 级 extraction 覆盖为站点定制规则（覆盖后置信度升至 0.8）。

### 4.4 dry-run 与正式抓取的统一（RunContext）

```ts
export type RunContext = {
  mode: "live" | "dry";
  persist(item: NormalizedTender, ctx: { skillCode: string }): Promise<void>;
  collect: { items: NormalizedTender[]; errors: string[] };   // dry 模式收集
};
```

- **live**：persist = 字段级 diff 入库（见 8.3）
- **dry**：persist = 推入 collect.items（截取前 20 条），其余管道完全一致
- API `POST /api/crawl/test`（ADMIN）：body `{skillCode, maxPages?, dryRun: true}` → 返回 `{items, extractionHits, errors, stats}`，响应标注「dry-run 未入库」

### 4.5 配置校验器（zod）

- YAML → `SkillConfigSchema.safeParse`：结构错误给出 JSON Path 级报错
- 语义校验：`mode: html` 必须有 `parse.itemSelector`；`extraFields` key ∈ 白名单；`regex` 可编译且长度 ≤ 200；`detail.extraction` 正则至少一个捕获组
- 选择器探活：仅在 dry-run 中执行——真实拉取一页后统计选择器命中率，0 命中报「itemSelector 未命中」并附页面 title 帮助定位改版

### 4.6 版本化流程

```
保存技能配置（后台）:
  YAML 输入 → zod 校验 → (可选 dry-run) → INSERT SkillRevision(version = max+1)
           → UPDATE CrawlSource.configVersion → 热更新生效（见 5.1）

回滚: 选择历史版本 → 内容复制为新版本 INSERT → 更新 configVersion
      —— 只前进不后退的版本链，保证审计完整
```

`SkillRevision` 全量保留（单份 YAML ≤ 20KB，增长极慢），不清理。

## 五、采集配置中心

### 5.1 配置加载与热更新（`crawler/config-loader.ts`）

**DB 为准绳，文件为开发态**：

```
loadCompiledConfig(skillCode, opts?: { file?: boolean }):
  file 模式（CLI --file / 本地调试）: 读 crawler/skills/<code>/config.yaml（现状行为不变）
  默认模式:
    1. SELECT SkillRevision WHERE skillCode = ? AND version = configVersion
    2. YAML.parse → zod 校验
    3. 与 CrawlSource 行合并运行参数：DB 非默认字段覆盖 config.settings 同名值
    4. 编译正则、解析 cron → CompiledConfig
       内存缓存 Map<skillCode, {version, compiled}>
  worker 每个任务开始前：SELECT configVersion 比对缓存 → 版本不同即重载
```

> 热更新因此零成本：**改 DB 配置 → 下一个任务自动生效**，worker 无需重启；后台保存动作只写库、不推送。

### 5.2 管理界面与操作清单

| `/admin/sources/[id]`（编辑） | 双 Tab：表单模式（调度/限速/代理/优先级）+ YAML 模式 | 保存 = 新 SkillRevision + 更新 configVersion |
| `/admin/sources/[id]/dry-run` | 解析样例表（前 20 条：映射字段 + 抽取命中高亮）+ 选择器命中率 + 错误列表 | 「重跑」「保存为版本」 |
| `/admin/sources/[id]/history` | SkillRevision 版本列表 + 行级 diff + 该源抓取日志 | 回滚（写入新版本） |
| `/admin/alerts` | 告警规则 CRUD + AlertRecord 最近触发记录 | 启停规则 |

所有变更走 Server Actions（沿用 `src/app/admin/actions.ts` 模式），记录操作人。

### 5.3 权限与安全

- 全部配置中心操作限 ADMIN（沿用现有 middleware + layout 双层校验）
- YAML 编辑无代码执行面——配置只是数据（选择器/正则/URL）；正则编译防 ReDoS：zod 阶段限长 ≤200、拒绝嵌套量词（启发式），运行时正则执行套整体超时保护

## 六、调度器与任务队列

### 6.1 调度循环（`crawler/scheduler.ts`）

```
每 60s（worker 进程内）:
  1. SELECT skillCode, scheduleCron, nextRunAt FROM CrawlSource WHERE enabled = true
  2. 对 nextRunAt IS NULL 或 nextRunAt <= now() 的源：
       a. nextRunAt' = cron-parser(scheduleCron, now)（写回）
       b. INSERT CrawlTask(skillCode, trigger='cron')    —— status=RUNNING 的源跳过
  3. 手动/重试任务由 API 直接入队（trigger='manual' | 'retry'）
```

- cron 语法沿用 5 段式（与 node-cron 同），新增依赖仅 `cron-parser`（计算下一次触发时间）
- 引入 `CrawlSource.nextRunAt` 后，调度决策退化为「比较一个时间戳」，无需每分钟解析所有 cron

### 6.2 任务池（`crawler/worker.ts` 重构）

```
TaskPool:
  并发上限 = env CRAWL_GLOBAL_CONCURRENCY（默认 2）
  循环: 取 queued 且 (nextRetryAt IS NULL OR nextRetryAt <= now) 的任务
        → UPDATE status='queued'→'running' 抢占（WHERE 守卫，多实例安全）
        → runSourceWithLogging(skillCode, {trigger})
        → 成功: done
          失败: attempts++ → attempts < maxAttempts ?
              重新入队（nextRetryAt = now + min(30min × 2^attempts, 24h)）
              : failed（写 error）
```

- `runSourceWithLogging` 保留 RUNNING 防重入（同一源不双跑）；trigger 落入 CrawlLog
- 运行参数全部来自 CompiledConfig（DB 优先）——「后台改配置 → 下次抓取即生效」

### 6.3 礼貌抓取全局不变量

- 单源请求间隔 `requestDelayMs`（现有逻辑保留）；全局并发 ≤ `CRAWL_GLOBAL_CONCURRENCY`
- 单源每频道每次页数 ≤ `maxPages`
- 同域名跨源任务加 3 秒错峰间隔（当前 ccgp 两源同域即受益）

## 七、健康分与监控告警

### 7.1 健康分算法（`crawler/health.ts`）

每次 `runSourceWithLogging` 结束后重算：

```
failRate7d = CrawlLog 近 7 日 status='FAILED' 条数 / 总条数      （不足 5 条时按 5 条折算）

score = 100
      − min(consecutiveFailures × 15, 45)                       （连续失败，封顶 45）
      − round(failRate7d × 40)                                  （近期失败率）
      − (now − lastSuccessAt > 2 × 期望调度间隔 ? 20 : 0)        （新鲜度超期）
      − (lastRun itemsParsed = 0 且 status = OK ? 10 : 0)        （空解析：页面疑似改版）

期望调度间隔 = 由 scheduleCron 推导（cron-parser 相邻两次触发差）
分级：≥90 健康（绿）/ 70–89 观察（黄）/ <70 失效（红）
```

计算结果写回 `CrawlSource.healthScore`；每次重算后跑一遍告警判定。

### 7.2 告警判定与通道（`crawler/alerts.ts`）

| condition | 触发 | 默认阈值 |
|---|---|---|
| health_below | healthScore < threshold | 70 |
| zero_parsed | status=OK 且 itemsParsed=0 | 1 次 |
| consecutive_failures | consecutiveFailures ≥ threshold | 3 |

- 判定循环挂在任务池消费完成后（事件驱动），不单独起定时器
- **冷却**：同规则 `cooldownMinutes` 内不重发（查 AlertRecord 最近触发时间）
- **通道**：email（nodemailer + SMTP 环境变量）与企业微信群机器人 webhook（一个 POST）；发送失败只记 console，不影响抓取主流程
- 恢复通知：源从红转绿时发一条「已恢复」（低成本高价值）

## 八、数据丰富化管道

### 8.1 七阶段管道（`runner.ts` 编排 + 各模块实现）

```
① 详情抓取        fetchDetail(html)
② 原文快照        Storage.put(contentHtml)  → contentHtml 字段（截断 200KB）
③ 结构恢复        normalize()（序号标题补换行，现有 tender-sections 逻辑）
④ 分节解析        parseTenderSections()（项目信息/资格/时间/联系方式/misc + 表格/链接块）
⑤ 结构化抽取      a. config.lists[].detail.extraction（站点定制，置信度 0.8）
                  b. config.lists[].parse.extraFields（列表页字段）
                  c. BUILTIN_EXTRACTION 兜底（置信度 0.6）
⑥ 转换与校验      EXTRA_FIELD_TARGETS 类型转换（decimal/datetime/phone/industry）
                  + 值域校验（金额 >0 且 <1e11；日期在 2000–2035）
⑦ 入库与派生      字段级 diff upsert → 项目聚合(projectNo/标题相似) → OrgContact upsert
                  → 附件发现（正文 <a href=*.pdf/doc/xls>）→ Attachment 行 + 下载队列
```

### 8.2 字段级 diff 入库（`crawler/persist.ts`）

现状 `upsertTender` 全量覆盖会抹掉人工修正；v2 规则：

```
对每个可仲裁字段 f ∈ {budgetAmount, awardAmount, openTime, expireDate,
                      projectNo, winningSupplier, purchaser, agency, ...}:
  incoming = 本次抽取值（含置信度 cIn、来源源 priority pIn）
  existing = 库中现值（含置信度 cOld、来源优先级 pOld）
  覆盖条件（全部满足才写）:
    existing 为空
    OR cIn > cOld                                    （更可信）
    OR (cIn == cOld 且 pIn > pOld)                   （同置信度，源优先级更高）
  title/content 始终以最新抓取为准（时效性优先），人工编辑过的 content 由
  fieldsConfidence["content"]=1.0 标记保护，规则抓取不覆盖
```

保护效果示例：运营在后台手工把某公告金额改为核实值（confidence 1.0）后，任何爬虫重抓都不会冲掉。

### 8.3 项目聚合（`crawler/projects.ts`）

```
对每条新/更新公告:
  1. projectNo 非空 → Project.findUnique({projectNo})
       命中 → projectRefId 关联；未命中 → 创建 Project
  2. projectNo 为空 → 归一化标题（去括号内容/「第X次」/空白/全半角）
       与近 90 天同省公告的 canonicalTitle 计算 bigram Dice 相似度
       ≥ 0.82 → 关联相似度最高者（并写入 fieldsConfidence 标记 0.6）
       < 0.82 → 仅聚合到「无编号孤儿池」，不建 Project（避免错合并）
  3. 每日批量任务重扫孤儿池（新公告到达可能补齐编号）
```

前台价值：详情页展示「该项目共 N 条公告：招标 → 变更 → 中标」时间线。

### 8.4 存储与生命周期（`crawler/storage.ts`）

- 接口：`put(key, buffer) / get(key) / delete(key)`，M0 实现为本地 `data/storage/` 目录（挂卷），接口与 S3/OSS 兼容，M2 平滑切云
- 原文快照：抓详情时同步写；保留 12 个月（定时清理任务按月归档删除）
- 附件：默认只登记不下载（pending）；铂金以上会员点击下载时按需拉取并转存（避免为无人下载的附件浪费带宽与存储）

## 九、PostgreSQL 迁移方案

### 9.1 五步迁移（M0 第一周，预计 1 天 + 2 天回归）

```
1. schema.prisma: provider = "postgresql"，补 @db.Decimal/@db.Text/Json 声明
2. npx prisma migrate dev 生成基线 migration（新库直接建表）
3. 数据搬运脚本 scripts/migrate-sqlite-to-pg.ts:
     SQLite 读 → 类型清洗（Decimal 字符串→字符串、日期时区统一 UTC）→ PG 写
     （当前数据量 ~300 条公告 + 地区表，秒级完成）
4. 方言回归:
     - LIKE 大小写：SQLite 的 LIKE 对 ASCII 不分大小写，PG 分大小写
       → query.ts 的 contains 在 PG 模式统一加 mode: "insensitive"
     - Prisma Json 字段读写行为核对（fieldsConfidence/fieldSources）
     - Decimal 序列化核对（Prisma 返回 Decimal.js 对象，展示层 toFixed）
5. 环境切换: DATABASE_URL 指向 PG；SQLite 文件保留 30 天作回滚兜底
```

### 9.2 回滚策略

切换后一周内发现问题：数据写入以 PG 为准，SQLite 仅作只读备份恢复来源（单向）。原因：双向同步成本高于一次冷回滚；且 M0 期用户量极小，可接受短暂回退窗口。

### 9.3 环境要求

Docker Compose 提供 `postgres:16`（app / worker / postgres / meilisearch[预留] 四服务），本地与生产同构。
